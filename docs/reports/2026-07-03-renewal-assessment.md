# プロジェクト刷新方針の検討レポート

- 作成日: 2026-07-03
- 種別: スナップショット（この時点の状況記録。以後の変更はここに反映しない）
- 前提: [2026-07-03 プロジェクト全体分析](2026-07-03-project-analysis.md) および [2026-07-03 追加課題調査](2026-07-03-additional-issues.md) を踏まえた刷新方針の検討。検討の出発点として、以下の4課題が挙げられた。
  1. 辞書のビルドや更新で手作業が多い
  2. 本番環境へのデプロイが手作業（OCI の VM 内で git pull して docker compose build）
  3. キーワードマッチの精度が低い（「シーズ」を拾いたいのに「シーズン」「seeds」まで拾う）
  4. フォーク元由来のアーキテクチャ・プログラミング言語が適切か不明

## 結論

**フルリライト（言語変更を含む書き直し）は行わず、段階的刷新を推奨する。** 4課題はいずれも言語やアーキテクチャの根本に起因する問題ではなく、運用の自動化と部分的な設計改修で解決できる。書き直しで得られるものは薄く、失うもの（テスト51件、Revert 往復を経て安定した実装、Sudachi ユーザー辞書の資産）のほうが大きい。

## 課題1: キーワードマッチの精度 — 誤検出の原因を特定

この時点の Sudachi システム辞書で実際に確認した結果:

```
'seeds' → normalized_form: 'シーズ'
'Seeds' → 'シーズ'
'SEEDS' → 'シーズ'
'シーズン' → 'シーズン'（1トークン。^シーズ$ には一致しない）
```

**Sudachi のシステム辞書が英単語 "seeds" を「シーズ」に正規化する**ため、rank1 の完全一致がこれを拾う。表記ゆれ吸収のために採用した正規化形マッチが、逆方向の衝突（無関係な英単語が固有名詞に正規化される）を引き起こしている構図。

なお「シーズン」は単体では `^シーズ$` に一致しないことを確認済み。「シーズン」が実際に誤検出されているなら別の分割パターンが絡んでいる可能性があり、実例の投稿を採取して特定する必要がある。

### 対策の方向性

- **短期**: 衝突しやすい短い語について、正規化形ではなく表面形（`surface()`）でマッチさせる語のリストを設ける。「シーズ」「SHHis」と書かれた投稿だけを拾い、"seeds" を除外できる。あるいは「シーズ」を rank2（文脈必須層）へ降格する。
- **中期**: 精度を本質的に上げるなら「現行ロジックで候補を広く拾う（高 recall）→ 曖昧な語にヒットした投稿だけ LLM または embedding で判定（高 precision）」の2段構えが本命。ボーダーライン投稿だけなら件数はわずかで、小型モデルでも判定コストはほぼ無視できる。

## 課題2: 辞書ビルドの手作業 — ローカル/本番乖離の解消とセットで

手作業そのものより、**user.csv が Docker ビルド時のみ組み込まれ、pytest が本番と異なる辞書で走っている**ことが本質的な問題（追加課題調査の通り、複数語 rank1 キーワードはローカルで構造的にマッチせず、テストで検証できない）。

- ローカルでも `sudachipy ubuild` を自動実行する仕組み（uv スクリプト＋conftest からの呼び出し）を入れ、テストを本番同等の辞書で走らせる。手作業削減とテスト信頼性向上が同時に解決する。
- keyword.toml のバリデーション（正規表現メタ文字チェック、rank1/rank2 の重複チェック等）を CI に載せる。

## 課題3: デプロイの手作業 — 最も費用対効果が高い改善

GitHub Actions で「テスト → イメージビルド（ユーザー辞書込み）→ GHCR に push → OCI VM で pull & 再起動（SSH ステップまたは Watchtower）」のパイプラインを構築する。辞書ビルドも同じパイプラインに乗るため、課題2の自動化と一体で解決する。刷新項目の中で最初に着手する価値がある。

## 課題4: アーキテクチャ・言語 — Python 継続が妥当、構造は2点改修

### 言語: Python 継続を推奨

このプロジェクトの生命線は日本語形態素解析であり、Sudachi のエコシステム（ユーザー辞書を含む）が最も成熟しているのが Python。atproto SDK も揃っている。TypeScript には公式 feed-generator リファレンスがあるが日本語 NLP が弱く、リライトの見返りがない。

### 構造: フォーク元由来の設計で直すべき点は2つ

1. **import 時副作用の解消（ingest / serve の分離）**: Firehose 購読スレッドが Flask アプリの import で起動する現設計は、gunicorn 1ワーカー制約・テストのしづらさ・graceful shutdown 問題（SIGTERM 未対応）の根源。「収集プロセス」と「配信 API」を compose 上の2サービスに分離すれば一掃できる。
2. **Firehose → Jetstream への移行**: 現在は生の Firehose を購読して CAR ブロックをデコードしており、Like/Follow まで無駄にデコードしている（全体分析レポートの指摘済み事項）。Bluesky 公式の Jetstream なら `wanted_collections=app.bsky.feed.post` で投稿だけを JSON で受信でき、帯域と CPU が大幅に減る。

### DB: SQLite 継続で十分

この規模では SQLite が適切。保持期限クリーンアップと `Post.uri` の unique 制約を追加すれば足り、DB 移行は不要。
