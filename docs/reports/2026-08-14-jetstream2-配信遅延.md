# jetstream2.us-east の配信遅延によるフィード遅延（2026-08-14）

## 事象

フィードに現れる最新投稿が約5時間前のものになっていた（未ログイン閲覧では約7時間前）。
同時に ingest が3時間に1回程度の頻度で切断・再接続を繰り返していた。

## 原因

購読先だった **`wss://jetstream2.us-east.bsky.network`（レガシー v1 ホスト）が、約5.2時間前の commit を「現在のイベント」として配信していた**。

公開4ホストへ同時接続し、`time_us`（ホストが付けるイベント時刻）と `record.createdAt`（投稿の作成時刻）の差を各400件で測定した結果（2026-08-14 04:12 UTC）:

| ホスト | `time_us` の最新 | `time_us` − `createdAt` 中央値 |
| --- | --- | --- |
| `jetstream2.us-east`（当時の購読先） | 実時刻 −7秒 | **5.20 時間** |
| `jetstream1.us-east` | 実時刻 −21秒 | 0.00 時間 |
| `jetstream.us-east`（v2） | 実時刻 −36秒 | 0.00 時間 |
| `jetstream.us-west`（v2） | 実時刻 −50秒 | 0.00 時間 |

25%点・75%点とも 5.20 時間で、全イベントが一様にずれていた（ホスト全体が定時間遅れで再生している状態）。

### 検知できなかった理由

**`time_us` には現在時刻が入ったままだった**ため、カーソルの遅延は 2 秒と正常値を示していた。
ingest のログ・カーソル・DB のいずれを見ても異常が観測できず、遅延はフィードの中身にしか現れなかった。

フィード側の実測でも裏付けが取れた。`getFeedSkeleton` のカーソル（＝各行の `indexed_at`）を1件ずつ復元し、投稿の `createdAt` と突き合わせた結果:

| # | createdAt | indexed_at | 収集までの遅れ |
| --- | --- | --- | --- |
| 1 | 08-13 22:58:22 | 08-14 04:10:39 | 5.20 時間 |
| 2 | 08-13 22:41:08 | 08-14 03:57:10 | 5.27 時間 |
| 5 | 08-13 20:08:18 | 08-14 02:01:27 | 5.89 時間 |
| 12 | 08-13 17:51:28 | 08-13 23:51:16 | 6.00 時間 |

先頭行の遅れ（5.20 時間）がホストの遅れと一致する。6.00 → 5.20 と縮んでおり、ホストは徐々に追いついていた。

## 切り分けの過程で否定した仮説

| 仮説 | 判定 |
| --- | --- |
| 切断・再接続によるデータ欠損 | ✗ カーソル再開で欠損なし。ログ上の最大遅延も14分 |
| ingest の処理能力不足 | ✗ 実測 16,824件/秒 に対し実ストリームは 66.8件/秒（251倍の余裕） |
| Cloudflare / App View のキャッシュ | ✗ オリジン直叩きでも `cf-cache-status: DYNAMIC` で同じ結果 |
| app と ingest が別 DB を見ている | ✗ スケルトンのカーソルから復元した `indexed_at` は最新（＝同一 DB） |
| 配信クエリの並び順の不具合 | ✗ `indexed_at DESC` は正しく機能していた |

## 対処

1. `JETSTREAM_ENDPOINT` を `wss://jetstream.us-east.bsky.network/subscribe` へ変更（v2 ホストは v1 ワイヤも提供するためコード変更は不要）。既定値も同ホストへ更新した。
   - **切り替え時はカーソルを巻き戻す必要がある。** 保存済みカーソルは壊れたホストの `time_us`（≒現在時刻）なので、そのまま健全なホストへ繋ぐと未取得の5.2時間分を飛ばしてしまう。
   - この巻き戻しは ingest の起動時処理として自動化した（購読ホストの変更を検知して8時間巻き戻す）。さらに戻す場合は `scripts/rewind_cursor.py --hours N`。
2. ingest に配信遅延の検知と接続の堅牢化を追加した（[architecture.md](../architecture.md) の該当節を参照）。

## 教訓

- **カーソルが追随していることは、収集内容が新しいことを意味しない。** Jetstream のカーソルはホスト自身が付けた時刻であり、ホストがネットワークから遅れていても正常値を示す。
- 監視すべき指標は `time_us` − `record.createdAt`。`createdAt` はクライアントの自己申告値なので中央値で見る。
- レガシーホスト（`jetstream1/2.*`）は凍結済みで、障害が起きても修正される保証がない。
